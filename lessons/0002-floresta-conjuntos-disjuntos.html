1. Representação: árvores e o vetor pai

Definição (slide "Florestas de conjuntos disjuntos")
  • Cada conjunto é uma árvore. O conjunto de todas as árvores é a floresta.
  • Cada nó representa um elemento e guarda um único ponteiro, para o seu pai. Não há ponteiro para os filhos.
  • A raiz aponta para ela mesma. É assim que se reconhece a raiz.
  • A raiz é o representante do conjunto: findSet(x) devolve a raiz da árvore de x.
  • Na forma mais simples, a floresta é um array de inteiros pai. O índice é o elemento e o valor é o pai desse elemento.

Lição 11.1: os conjuntos {5, 0, 6, 1} e {3, 2, 7, 4} como listas ligadas. Todo nó aponta direto para o conjunto (rep).

Os mesmos dois conjuntos como floresta. Cada seta vai do filho para o pai, e o laço em cima da raiz é pai[r] = r. Raízes: 5 e 3.

A diferença principal: na lista, todo elemento chega ao representante em 1 passo (rep). Na floresta, ele precisa subir pela árvore até a raiz, e o número de passos depende da profundidade. Em compensação, juntar duas árvores muda um único ponteiro (seção 6), enquanto na lista era preciso corrigir o rep de cada nó anexado.

2. Do vetor para o desenho (e de volta)

Na prova o enunciado dá o array e você precisa enxergar as árvores. Use este procedimento:

  1. Ache as raízes: os índices com pai[i] = i. Cada raiz é uma árvore.
  2. Para cada outro i, desenhe uma seta i → pai[i]. Quem tem pai[i] = r fica no nível 1 abaixo de r, quem aponta para esses fica no nível 2, e assim por diante.
  3. Confira: partindo de qualquer nó e seguindo as setas, você precisa chegar a uma raiz.

3. makeSet

makeSet(x)
1.  pai[x] = x

Cria uma árvore de um nó só, que é a própria raiz. É uma atribuição: $O(1)$. No começo do Kruskal, depois dos $V$ makeSet, a floresta fica assim (8 conjuntos, 8 raízes):

4. findSet passo a passo, com a pilha de chamadas

findSet(x)
1.  if pai[x] = x then
2.      return x
3.  return findSet(pai[x])
  • Linha 1: x aponta para si mesmo? Então x é a raiz.
  • Linha 2: caso base. Devolve x, que é o representante.
  • Linha 3: caso recursivo. "A raiz de x é a raiz do pai de x." Sobe um nível e pergunta de novo. A chamada atual fica esperando a resposta e depois só a repassa para cima.

São duas fases. Na ida, as chamadas se empilham subindo da folha até a raiz. Na volta, a raiz encontrada é devolvida chamada por chamada, até a primeira.

findSet(x), passo a passo

Azul: chamada atual. Laranja: nó já visitado e a seta seguida. Verde: raiz. No array, a célula lida em cada passo fica destacada. À direita, a pilha: cada nova chamada entra embaixo, e na volta cada uma mostra o que devolveu.

Versão iterativa, equivalente (útil para entender o custo) 
findSet(x)
while pai[x] ≠ x do
    x = pai[x]
return x

Mesmo caminho, sem pilha. O laço roda uma vez por aresta do caminho até a raiz, ou seja, profundidade(x) vezes.

5. Custo do findSet: melhor e pior caso

Cada chamada faz trabalho constante (uma leitura, uma comparação e no máximo uma chamada). O número de chamadas é o número de nós no caminho de x até a raiz:

chamadas = profundidade(x) + 1, então custo = $\Theta(\text{profundidade}(x) + 1)$

Melhor caso: x já é a raiz (ou a árvore é "rasa"). findSet(3) faz 1 chamada: $O(1)$.

Pior caso: todos os $n$ elementos numa árvore completamente desbalanceada, que é uma lista. findSet(7) sobe por todos: $n$ chamadas, $O(n)$.

Resposta de prova: "complexidade do find em função de n? Existe melhor e pior caso?"

Sim. O custo depende da profundidade do nó, porque o find sobe um nível por chamada até a raiz. Melhor caso $O(1)$: x é a raiz (pai[x] = x), uma única comparação. Pior caso $O(n)$: os n elementos estão numa só árvore degenerada em lista (cada nó aponta para o anterior) e x é a folha do fim, então o find percorre os n nós. Sem heurísticas nada impede que esse formato apareça, porque o union pode criar árvores assim (seção 7).

6. union: três ideias, só uma serve

O slide constrói o union em três tentativas. A animação usa o mesmo começo nas três: duas árvores de altura 2 e a chamada union(1, 4).

union(1, 4): compare as três ideias

Laranja: caminho percorrido por um findSet. Verde: o único ponteiro que o union altera. Vermelho: elementos que ficaram no conjunto errado. Repare como os nós deslizam para a nova posição quando a seta muda.

IdeiaCódigoResultado em union(1, 4)
1. ligar x a ypai[x] = yErrado. Só o 1 (e o que estiver abaixo dele) muda de árvore. 5, 0 e 6 ficam de fora. Funciona só se x for raiz.
2. ligar a raiz de x a ypai[findSet(x)] = yCorreto, todos ficam numa árvore. Mas a altura vai de 2 para 5: a árvore de 1 foi pendurada embaixo do 4, que já era fundo.
3. ligar raiz a raizpai[findSet(x)] = findSet(y)Correto, e a altura fica 3. É a versão do slide.
union(x, y)
1.  pai[findSet(x)] = findSet(y)

Custo: a atribuição é $O(1)$. As duas chamadas de findSet dominam, e cada uma é $O(n)$ no pior caso (duas árvores-lista). Portanto union = $O(n)$ no pior caso.

7. Listas × floresta, e o problema da altura

Função (pior caso)Listas ligadasFloresta
makeSet$O(1)$$O(1)$
findSet$O(1)$$O(n)$
union$O(n)$$O(n)$

Pela tabela, a floresta parece pior. O que estraga tudo é a altura: o custo do findSet, e por consequência do union, é a profundidade. Mesmo usando a ideia 3, o union pode produzir árvores altas. Exemplo, começando com 8 conjuntos unitários: union(0,1), union(1,2), …, union(6,7). Em cada chamada, findSet(x) devolve a raiz atual da árvore inteira, que é pendurada no próximo elemento sozinho. O resultado é uma lista:

Depois de union(6,7): 8 elementos, altura 7. findSet(0) faz 8 chamadas.

Os mesmos 8 elementos com altura 2. findSet em qualquer nó: no máximo 3 chamadas.

O slide resolve isso com duas heurísticas: union by rank, que pendura a árvore mais baixa na mais alta e garante altura $\le \log_2 n$ (Lição 11.3), e path compression, que achata o caminho durante o findSet (Lição 11.4).
